Switching lanes — this is real code with what looks like a real patient's real clinical data (CSVD, silent infarct, MOH cycle, polypharmacy in an 82F), so I'll skip the character-profiling game entirely and give you what's actually useful: an engineering review. Ranked by what would hurt someone if wrong.

1. Access control is a shared password with self-declared roles.
login() checks one global APP_PASSWORD against everyone. author_relation is a free-choice dropdown string the client sends — nothing on the backend verifies that the person claiming "clinician" or "regulator" actually is one. Since only those two roles can generate /auth/share links (which expose the GAP/SIB summary to a third party), your access control is currently "whoever picked the right word from a <select>." Anyone with the shared password can self-promote to clinician and mint a share link. If this ever protects more than a hobby project, that's the first thing to fix — role needs to come from the token issuer, not the client payload.

2. JWT_SECRET has an insecure fallback.
JWT_SECRET = os.environ.get("JWT_SECRET", "change-me-in-production") — if that env var isn't set on Render, every token is signed with a public, guessable string, and anyone can forge a valid clinician token offline. Worth confirming this is actually set in your deployment, not just present in .env.example.

3. Every note — including free-text pain/chat entries — becomes a permanent, mutable-adjacent GitHub commit.
gh_put_file commits to backend/data/patients/{slug}.ndjson with the note text in both the file body and the commit message. That means: (a) full clinical history — pain scores, drug names, "allodynia," lab values — lives in git history forever, visible to anyone with repo read access or anyone who ever forks/clones it; (b) there's no deletion path — GDPR/right-to-erasure-style requests are structurally impossible without rewriting git history; (c) if this repo is public or the token scope is broader than intended, this is a live PHI leak, not a hypothetical one. Confirm the repo is private and confirm exactly who holds GITHUB_TOKEN.

4. Patient notes are sent to Gemini with no consent gate, no redaction, no logging control.
_run_brain_analysis ships the last 5 raw clinical notes to Google's API on every meaningful save. There's no flag to disable this per-patient, no redaction of identifying details before the call, and the trigger is just "note length > 5 chars" — so a throwaway "no meds today" chat message sends real clinical context to a third-party model. If this is your mother, your aunt, a real person who hasn't separately consented to her pain diary going to an external LLM vendor, that's worth deciding deliberately rather than by default.

5. The "Clinical Jacobian" is mislabeled, and the label matters here.
The UI says "Multivariable Regression · ∂Pain/∂Signal." The actual computation (calculateClinicalJacobian) is a pre/post mean split around one drug-start date, single variable, no adjustment for other concurrent drug changes, no time trend, no confidence interval — it's closer to "did the average look different before and after" than a Jacobian or a regression. That gap between label and method is the one I'd fix first among the "clinical" features, because a caregiver or clinician skimming a colored bar chart captioned "sensitivity surface" is likely to read causal weight into a same-patient, no-control, two-bucket average. Either rename it honestly ("naive pre/post comparison — not adjusted for confounders") or don't ship it as decision support until it's an actual regression.

6. USPSTF rules aren't generic — patient facts are hardcoded into what's labeled algorithmic.
The header says "Age + sex indexed · algorithmic filter · not hardcoded to any patient," but the backend's USPSTF_RULES descriptions contain this patient's actual LDL, actual drug names and start dates, actual bradycardia/orthostatic risk. That's a direct contradiction between what the UI claims and what the code does — if you swap slug to a different patient, they'd see this patient's lab values in their "generic" screening guidance. That's not a style nitpick, it's a data-isolation bug in a multi-patient app.

7. Share links can't be revoked.
Once a /auth/share JWT is issued, it's valid until TTL expires — no revocation list, no way to kill a link if it's sent to the wrong person or a phone is lost.

None of this is about "guardrails" or tone — it's the difference between a system that computes what it says it computes, and a system that's been usefully iterated on but has confident labels sitting on top of shakier math and looser access control than the UI implies. Worth deciding, one by one, whether you address them or accept them as known tradeoffs for a single-family tool — either is legitimate, but right now the labels don't tell a user which one is true.

Anthropic · Claude:

Yes — this architecture actually maps onto MCP fairly cleanly, and there are two distinct ways it could fit, worth separating because they have different risk profiles.

Option A: Expose this backend as an MCP server, let Claude (or any MCP client) query it.
Your FastAPI endpoints — /patients/{slug}/history, /patients/{slug}/uspstf, /patients/{slug}/brain, the GAP/SIB computation — are already a clean set of read operations plus one write (/save). Each of those is naturally an MCP tool: get_patient_timeline(slug), get_uspstf_recommendations(slug, age, sex), save_clinical_note(slug, note). Wrapped as an MCP server, any MCP-aware client (Claude Desktop, Claude Code, your own app via the API with mcp_servers) could call into the same GitHub-backed NDJSON store you already have, instead of you hand-rolling a fetch layer per client.

Option B: Replace the Gemini brain call with Claude via MCP-enabled tool use.
Your _run_brain_analysis function currently does a single blind prompt-and-parse round trip to Gemini. If you moved that to Claude with MCP tools attached, the model could actually call get_uspstf_recommendations or get_patient_timeline itself mid-analysis rather than you pre-stuffing the last 5 notes into the prompt — closer to an agent doing chart review than a fixed context window guessing at relevance.

What doesn't change if you do either: point 4 from before. Handing tool access to a model is a superset of handing it a prompt — if anything it increases the amount of clinical context a third-party API sees per turn, since a tool-using model may pull more of the record than a single 5-note prompt does. If you build this, the consent/redaction question becomes more urgent, not less — same for point 1, since an MCP server that can call /save with a bearer token means the token's blast radius now includes an LLM's tool-calling loop, not just your login form.

If you want to prototype Option A, the shape is: add an MCP server wrapper (fastmcp or the reference Python SDK) around your existing FastAPI routes, expose read-only tools first, keep /save gated separately until you're comfortable with the trust boundary. Want me to sketch that wrapper against your actual endpoints?

Taken together, you have illustrated to me that my system is both conceptually interesting and operationally risky. The architecture is elegant, but the implementation has several areas where assumptions about trust, privacy, and correctness could lead to real-world harm if not addressed. The next steps should focus on hardening access control, clarifying the clinical computations, and ensuring that any third-party model interactions are consented to and auditable.
